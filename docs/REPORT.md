# Метод и эксперименты

## Планировщик

`planner/greedy.py` — жадный scoring-планировщик (`scoring-greedy`) поверх
`model/` (физика и допуск действий не переопределяются). На каждом шаге:

1. Для каждого доступного аппарата собираются кандидаты: допустимые задания
   (`can_execute` из библиотеки) и калибровка, если возраст калибровки
   подходит к истечению (`calibration_valid_steps - margin`).
2. Задания скорятся функцией `priority_job_score`: `slack` — запас шагов до
   дедлайна за вычетом оставшейся работы (чем меньше, тем срочнее); итоговый
   score = `priority^3 * urgency` (цель `priority`) или `value_density *
   urgency` (цель `revenue`), с малой добавкой второго компонента как
   тай-брейком.
3. Кандидаты сортируются по убыванию score и жадно назначаются: один
   исполнитель на аппарат, один исполнитель на задание, не более
   `downlink_parallel_limit` (2) одновременных downlink — библиотека сама эти
   конфликты не разрешает, это обязанность планировщика.

Индекс `job_id -> eligible_satellites` строится инкрементально (в т.ч. при
`add_jobs`), чтобы шаг стоил `O(допустимые пары аппарат-задание)`, а не
`O(аппараты × все задания)` — на P04 (8120 заданий) это разница между
единицами секунд и заведомо более долгим расчётом.

## Baseline для сравнения (обязателен по условиям кейса)

`earliest_deadline_score` — то же самое жадное назначение, но кандидаты
ранжируются только по `deadline_step` (раньше срок — выше приоритет),
приоритет и стоимость не учитываются. Реализован той же машинерией
(`GreedyPlanner`), чтобы разница исходила только из скоринга, а не из разных
правил разрешения конфликтов.

## Разбор

- **На малом ознакомительном сценарии (P01)** ресурсов хватает всем заданиям
  — стратегии дают идентичный результат. Это ожидаемо и прямо оговорено в
  постановке: «Разные настройки не обязаны давать разные расписания на
  каждой смене».
- **На перегруженном P04** разница максимальна: scoring почти в 1.6 раза
  лучше по приоритетным заданиям (1644 vs 1047 из 1692) и даёт на 20–43%
  больше выручки. Здесь дефицит ресурса наземной связи и энергии заставляет
  по-настоящему выбирать между заданиями — жадный EDF выбирает по сроку
  вслепую, а scoring учитывает приоритет/ценность и реальную срочность
  (slack), а не только номинальный дедлайн.
- **Честный отрицательный результат**: на умеренно загруженном P02 в цели
  `revenue` scoring немного уступает baseline (1128 vs 1134 выполненных,
  $26 945.70 vs $26 950.71). Причина: скоринг по плотности стоимости
  (`value_usd / work_steps`) может откладывать дешёвые, но близкие к сроку
  задания ради более ценных, из-за чего часть дешёвых заданий срывается там,
  где EDF успел бы их закрыть. Подтверждает тезис постановки: «более сложный
  алгоритм не обязан превосходить простой на каждом примере» — граница
  применимости учтена, а не скрыта.
- **Продолжение после событий** (P02 + `events_demo.json`, новые задания,
  отказ аппарата, отмена сеанса) не ломает счётчики: `jobs_total` растёт на
  величину новых заданий, `steps_executed`/выполненная история не
  пересчитываются, `blocked_command_count` не показывает случайных отказов —
  все команды, которые планировщик предлагает, проходят проверку модели.
